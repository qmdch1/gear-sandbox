# Gear Sandbox v2 — 정밀 맞물림 + 제조업 표준 오브젝트 세트 설계 문서

- **날짜**: 2026-08-27
- **분류**: 아키텍처(architectural) — 기존 프로젝트([2026-08-18 설계](2026-08-18-gear-sandbox-design.md))의 증분 확장
- **한 줄 요약**: (1) 톱니가 실제로 인터리브되어 맞물리는 정확한 지오메트리/위상 정렬로 "겹침처럼 보이는" 렌더링 버그를 근본적으로 없애고, (2) 실제 산업 동력전달에서 흔히 쓰는 6종 오브젝트(랙&피니언, 유성기어, 래칫, 스프로킷+체인, 풀리+벨트, 차동장치)를 추가해 기존 6종과 합쳐 총 12종 오브젝트를 지원한다.

## 0. 배경 — 왜 필요한가

기존 구현(`src/render/gearGeometry.ts`)의 톱니 프로파일은 이빨당 4점(바깥/안쪽 반지름 교대)짜리 사각파형이고 `curveSegments: 1`이라 곡선이 없다. 더 결정적으로, 맞물림 판정(`evaluatePair`)은 **중심간 거리·축 방향만** 검사하고 **두 기어의 톱니 위상(회전각)** 은 전혀 맞추지 않는다 — 그래서 유효하게 "맞물렸다"고 판정된 두 기어도 초기 배치 시점의 임의 회전각 그대로 렌더링되어, 이가 서로의 톱 사이 홈이 아니라 상대 이빨 몸통을 뚫고 지나가는 것처럼 보인다(사용자가 말한 "이빨 안 물리고 이미지 겹치는" 현상). 베벨은 이가 없는 매끈한 원뿔(`ConeGeometry`), 웜은 나사산 없는 매끈한 원기둥이라 애초에 "물리는 그림"이 나올 수 없다.

## 1. 목적 & 범위

- v1과 동일하게 목표/점수 없는 샌드박스. 이번 증분은 (A) 시각 정확도 버그 수정, (B) 오브젝트 카탈로그 확장 두 갈래.
- **비목표(변경 없음, v1 §1 유지)**: 계정/인증, 멀티플레이어, 정밀 강체 물리(자유낙하·충돌). **신규 비목표**: 차동장치의 실제 좌우 속도차 분배(§3.6에서 이유 설명), 벨트/체인의 슬립·장력 시뮬레이션, 유성기어 내부 위성기어 개별 시뮬레이션(§3.5).
- **순서**: (A) 먼저 — 기존 6종에 대해 톱니 지오메트리/위상 정렬을 고쳐서 "제대로 물리는" 상태를 만든 뒤, (B) 그 위에 신규 6종을 얹는다. 신규 타입도 처음부터 고쳐진 지오메트리 파이프라인으로 나온다.

## 2. (A) 시각 정확도 수정

### 2.1 톱니 프로파일 — 사다리꼴 근사를 인볼류트 곡선으로 교체 (검증됨)

- **왜 사다리꼴 근사로는 안 되는지 실측 검증**: "위상을 한 번만 맞추면 이후 회전 중에도 자동으로 안 겹친다"는 게 이번 개정 전 초안의 핵심 전제였는데, 이걸 순수 수치 시뮬레이션(`.scratch/overlap_depth_verify.ts`, 이 저장소에는 커밋하지 않는 임시 검증 스크립트)으로 직접 계산해보니 **거짓으로 확인됐다**. 사다리꼴(비인볼류트) 프로파일은 접점에서 위상을 완벽히 맞춰 시작해도, 두 기어의 회전이 진행됨에 따라 위상이 어긋나며 한 바퀴 안에서 반복적으로 이빨 끝(addendum)끼리 정면 간섭한다(테스트한 5가지 잇수 조합 모두에서 최대 간섭 깊이가 이빨 높이의 대부분에 달함). 이는 사다리꼴 프로파일이 등속비·무간섭을 보장하는 "공액 곡선(conjugate curve)" 성질을 갖지 않기 때문 — 실제 산업 기어가 예외 없이 인볼류트 곡선을 쓰는 바로 그 이유다.
- 따라서 `computeSpurProfilePoints`를 사다리꼴 근사가 아니라 **표준 인볼류트 치형**으로 교체한다:
  - 압력각(pressure angle) 20°(업계 표준) 고정.
  - 기초원 반지름 `baseRadius = pitchRadius * cos(20°)`.
  - 인볼류트 곡선의 매개변수식: `x(t) = baseRadius * (cos(t) + t*sin(t))`, `y(t) = baseRadius * (sin(t) - t*cos(t))` — `t`는 0부터, 곡선 반지름이 addendum원(`pitchRadius + module`)에 닿는 지점까지.
  - 표준 비례: addendum = 1.0×module, dedendum = 1.25×module(치형 뿌리에 여유를 더 둠 — 이 비대칭이 맞물릴 때 팁과 뿌리 사이 여유(clearance)를 보장).
  - 이 값의 반쪽 곡선을 Y축 대칭시켜 이 하나의 좌/우 플랭크를 만들고, 잇수만큼 회전 복제해 전체 프로파일 점 목록을 만든다(치형 사이 간격은 표준 원주피치 공식 `π×module/2`로 계산).
  - 잇수가 매우 적을 때(< 8) 인볼류트가 기초원보다 안쪽에서 시작해 언더컷이 생길 수 있으나, 이 프로젝트의 오브젝트들은 실사용상 잇수 8 미만을 잘 쓰지 않고 시각적 샌드박스이므로 언더컷 보정은 다루지 않는다(§7 향후 확장 후보로 유지).
- `ExtrudeGeometry`의 `curveSegments`를 1 → 2로 올려 각진 결을 완화한다(성능 영향 미미).
- **왜 이게 실제로 겹침을 없애는지(수학적 근거, 재검증 불필요)**: 같은 모듈·같은 압력각의 인볼류트 치형 한 쌍을 표준 중심거리(피치반지름의 합)로 배치하면, 등속각속도비와 무간섭이 곡선의 기하학적 성질 자체로 보장된다 — 이것이 인볼류트 곡선이 1700년대 이래 모든 산업 기어의 표준 치형인 이유이며, 이 프로젝트가 임의로 발명한 근사가 아니라 검증된 공학 공식을 그대로 적용하는 것이다.

### 2.2 위상 정렬 (핵심 수정)

- 새 순수 함수 `computeMeshPhaseOffset(a: GearInstance, b: GearInstance, edge: MeshEdge): number`를 `src/sim/meshing.ts`에 추가한다. 두 기어가 맞물리는 접점에서 A의 이빨 중심과 B의 홈 중심이 일치하도록, "B가 가져야 할 회전각 오프셋"을 A의 현재 회전각·두 기어의 위치·잇수로부터 계산한다. 공식은 §2.1의 인볼류트 치형 전환을 전제로 검증됐다(`.scratch/phase_offset_verify.ts`로 임의 축 방향·잇수 조합에서 THREE.js의 쿼터니언 기반 월드 좌표계와 순수 TS(Rodrigues 회전 공식) 재구현이 오차 1e-15 수준으로 일치함을 확인 — 시뮬레이션 코어가 THREE.js에 의존하지 않아도 렌더링과 동일한 로컬 좌표계를 재현할 수 있다는 전제가 성립).
- 이 오프셋은 **두 기어가 새로 맞물리는 순간(그래프에 새 엣지가 생기는 틱)에 한 번만** 적용해 B의 `rotation`에 더한다 — §2.1에서 인볼류트 치형으로 바꿨기 때문에(사다리꼴이 아니라), 이후에는 `propagateRotation`이 이미 올바른 비율로 각속도를 전파하고 있으므로(v1에서 검증됨) 상대 위상이 자동으로 유지된다는 주장이 성립한다. 사다리꼴 프로파일이었다면 이 주장이 성립하지 않는다는 걸 §2.1에서 실측으로 확인했다.
- `tick()`(`src/sim/simulation.ts`)이 이전 틱의 엣지 집합과 이번 틱의 엣지 집합을 비교해 새로 생긴 엣지에 대해서만 `computeMeshPhaseOffset`을 적용한다(기존 `computeSyncActions`가 add/remove 기어를 diff하던 것과 같은 패턴을 엣지 집합에 적용).
- 체인/벨트(§3.3, §3.4)는 톱니가 맞물리는 게 아니라 접선으로 감기므로 위상 정렬 대상에서 제외.

### 2.3 베벨 / 웜 실지오메트리

- 베벨: 원뿔 표면에 방사형 이빨 홈을 낸 지오메트리로 교체(원뿔 프로파일을 §2.1의 사다리꼴 톱니 프로파일로 반지름별로 스케일해 적층 압출 — 기존 `extrudedGearGeometry`의 원뿔 버전).
- 웜: 원기둥 표면에 나선형 홈을 낸 지오메트리로 교체(원기둥을 나선을 따라 스윕하는 좁은 나사산 리본 형태 — `computeSpurProfilePoints`와 별개의 `computeWormThreadPoints` 헬퍼).

## 3. (B) 신규 오브젝트 6종

기존 6종(spur/helical/crank/bevel/worm/load)에 추가. `GearType` 유니온에 6개 리터럴 추가.

| 오브젝트 | 설명 | 회전/동력 특성 | 시뮬레이션 단순화 |
|---|---|---|---|
| **랙 (Rack)** | 직선 톱니 막대. 피니언(평/헬리컬 기어)과 맞물려 회전을 직선 이동으로 변환 | 맞물린 피니언의 각속도 × 피치반지름 = 랙의 선속도. 랙은 더 이상 동력을 전달하지 않는 말단(leaf) | §3.1 |
| **유성기어 세트 (Planetary)** | 선기어·유성기어·링기어를 하나의 조립체로 표현 | 기존 평기어 계열과 동일한 방식(중심거리+평행축)으로 맞물리되, 고정된 큰 감속비(웜과 비슷한 포지셔닝)를 가짐 | §3.5 |
| **래칫 기어 (Ratchet)** | 평기어처럼 맞물리지만 역구동 불가(폴(pawl)이 한쪽 방향만 허용) | 맞물린 상대는 래칫을 돌릴 수 있지만, 래칫은 상대를 돌릴 수 없음(웜의 `oneWay`와 동일 메커니즘 재사용) | 없음(정확한 실제 거동) |
| **스프로킷 (Sprocket) + 체인** | 이가 있는 바퀴, 인접하지 않아도 체인으로 원거리 연결 가능 | 체인으로 이어진 두 스프로킷은 **같은 방향**으로, 잇수비만큼 회전(기어 맞물림과 달리 방향 반전 없음) | §3.3 |
| **풀리 (Pulley) + 벨트** | 스프로킷과 동일 개념이나 이가 없는 매끈한 바퀴(마찰 구동) | 스프로킷과 동일 로직, 잇수 대신 반지름비 사용. 슬립 없음(이상적 벨트 가정) | §3.4 |
| **차동장치 (Differential)** | 입력 1축(베벨 링기어) → 출력 2축(좌우 바퀴 축) | 입력축과 두 출력축 모두 같은 각속도로 회전(잠금 차동 취급) | §3.6 |

### 3.1 랙 (Rack)

- `GearInstance`에 옵션 필드 `linearPosition?: number`(랙 전용, 그 외 타입은 `undefined`) 추가. 랙은 `axis` 방향을 따라 `linearPosition`만큼 로컬 이동한다.
- 맞물림 판정: 피니언 중심에서 랙의 이동축 직선까지의 거리 ≈ 피니언 피치반지름(오차범위는 기존 `MESH_TOLERANCE` 재사용), 축은 피니언 회전축과 랙 이동축이 직교.
- `propagateRotation`이 랙 노드에 도달하면 각속도 대신 `linearVelocity = pinionAngularVelocity × pinionPitchRadius`를 계산해 별도 맵에 기록하고, `tick()`이 매 틱 `linearPosition += linearVelocity × dt`로 누적한다(각도 회전 누적과 대칭 구조).
- 랙은 leaf이므로(테이블 §3 "더 이상 동력을 전달하지 않는") 그래프 전파상 자식을 갖지 않아도 되지만, 구현은 일반 노드와 동일하게 두고 "랙에서 나가는 엣지는 만들지 않는다"는 규칙만 `evaluatePair`에 추가(대칭성보다 단순성 우선 — 랙끼리 또는 랙-랙 뒤 물체 연결은 요구사항에 없음).

### 3.2 래칫 (Ratchet)

- `meshing.ts`의 `PARALLEL_FAMILY`에 래칫을 추가하되, 한쪽이 래칫이면 `oneWay`를 상대→래칫 방향으로 고정(웜의 `wormPair` 분기와 병렬 구조의 새 분기, 코드 중복보다 명료성 우선 — 두 분기가 각각 다른 기하 조건(평행축 vs 직교축)을 검사하므로 억지로 합치면 오히려 읽기 어려움).

### 3.3 스프로킷(Sprocket) + 체인, 3.4 풀리(Pulley) + 벨트

- 이 둘은 **기하학적 근접성으로 자동 판정되지 않는 유일한 연결**이다 — 체인/벨트는 임의의 거리에서 사용자가 명시적으로 "이 둘을 연결"이라고 지정해야 한다.
- 데이터 모델: 최상위 레이아웃 상태에 `remoteLinks: Array<{ a: string; b: string; kind: "chain" | "belt" }>`를 추가(개별 `GearInstance`가 아니라 레이아웃 전체 상태에 귀속 — 저장/직렬화 스키마 버전 2로 마이그레이션, §6).
- `buildEdges(gears, remoteLinks)`가 기존 기하 기반 엣지에 `remoteLinks`를 순회해 만든 엣지를 합친다. 체인/벨트 엣지는 `oneWay: "none"`, **방향 반전 없이**(`sign = +1`, 기존 기어 맞물림의 `sign = -1`과 대비) 잇수비(체인) 또는 반지름비(벨트)로 각속도를 전달.
- UI: 팔레트에서 스프로킷/풀리를 배치한 뒤, 하나를 클릭 → 다른 하나를 클릭하면 연결(기존 `onSelect` 콜백 확장 — "연결 모드" 토글 버튼을 사이드 패널에 추가). 3D 씬에는 두 축 사이에 체인/벨트 형상의 얇은 리본 메시를 그린다(양 끝점만 있으면 되므로 지오메트리는 간단한 `TubeGeometry` 또는 두 원 사이 공통 접선 스트립).

### 3.5 유성기어 (Planetary)

- 시뮬레이션 노드는 **하나**(선기어+유성기어+링기어를 각각 시뮬레이션하지 않음) — 개별 위성기어의 위상까지 맞추는 건 이번 스코프의 이득 대비 복잡도가 과함(YAGNI, v1 §1 "정밀 강체 시뮬레이션 아님" 원칙의 연장). 링기어 외곽을 기준으로 평기어 계열과 동일한 거리/평행축 규칙으로 맞물리며, `GEAR_DEFS.planetary`에 웜과 비슷하게 큰 고정 감속비 성격의 `baseWearPerSecond`/`durabilityMax`를 부여한다.
- 지오메트리만 3중 구조(중심 선기어 실린더 + 방사형 배치된 3~4개 소형 유성기어 + 외곽 링기어 이빨)로 조립해 "유성기어처럼 보이게" 렌더링 — `mergeGeometries` 기존 헬퍼 재사용.

### 3.6 차동장치 (Differential)

- 왜 "잠금 차동"으로 단순화하는가: 실제 차동장치는 좌우 바퀴가 노면 저항에 따라 다른 속도로 돈다 — 이는 **토크/저항을 모델링해야** 계산 가능한데, 이 시뮬레이션 코어는 v1부터 순수 운동학(각속도 전파)만 다루고 부하는 "마모 배수"로만 반영할 뿐 저항에 의한 속도 변화는 다루지 않는다(v1 §1 비목표). 따라서 두 출력축은 입력과 동일한 각속도로 함께 돈다. 이 단순화는 스펙에 명시해 사용자가 "차동장치인데 왜 항상 양쪽이 똑같이 도나"라는 혼란을 피하게 한다(UI 툴팁에도 노출).
- 맞물림: 입력축(베벨 링기어 자리)은 기존 베벨 규칙 재사용, 두 출력축은 입력 노드에 좌우 대칭으로 코인시던트 커플링(로드 오브젝트의 커플링 규칙과 동일한 기하 조건, ratio=1).

## 4. 데이터 모델 변경

```ts
export type GearType =
  | "spur" | "helical" | "crank" | "bevel" | "worm" | "load"   // v1
  | "rack" | "planetary" | "ratchet" | "sprocket" | "pulley" | "differential"; // v2

export interface GearInstance {
  // ...v1 필드 전부 유지...
  linearPosition?: number; // rack 전용
}

export interface MeshEdge {
  // ...v1 필드 전부 유지...
  kind: "mesh" | "coupling" | "chain" | "belt"; // "chain"/"belt" 추가
}

export interface LayoutState {
  gears: GearInstance[];
  remoteLinks: Array<{ a: string; b: string; kind: "chain" | "belt" }>; // 신규
}
```

`tick()`의 시그니처가 `tick(gears, dt, timeScale)` → `tick(layout: LayoutState, dt, timeScale)`로 바뀐다 — `remoteLinks`를 엣지 생성 단계에서 함께 넘겨야 하므로. 호출부(`main.ts`, 각 UI 패널)는 이 변경에 맞춰 갱신.

`GEAR_DEFS`(`src/sim/gearDefs.ts`)에 신규 6종 각각의 `durabilityMax`/`baseWearPerSecond`/`loadWearMultiplier` 항목을 추가한다 — v1과 동일하게 정확한 수치는 구현 중 튜닝(예: 래칫은 폴 마모를 반영해 평기어보다 낮은 내구도, 유성기어는 부품 수가 많은 만큼 평기어보다 높은 내구도 등 정성적 방향만 이 문서에서 정하고 실제 값은 Task 구현 시 테스트로 고정).

## 5. 테스트 접근 (v1 §9 원칙 유지)

- 위상 정렬(`computeMeshPhaseOffset`), 랙 선속도 변환, 래칫 `oneWay` 방향, 체인/벨트 방향-비반전 규칙, 차동장치 양쪽 동일 속도 — 전부 순수 함수라 v1과 동일하게 단위 테스트로 충분히 커버.
- 지오메트리(베벨/웜 실톱니, 유성기어 조립)는 v1의 `gearGeometry.test.ts` 패턴대로 "정점 수 > 0", "바깥반지름이 안쪽보다 큼" 같은 형상 불변량만 검증 — 렌더링 결과의 미적 판단은 수동 QA.
- 체인/벨트 연결 UI(클릭-클릭 연결 모드)는 v1의 `dragControls`처럼 포인터 이벤트 기반이라 수동 QA 위주, 연결 상태 저장/복원 로직만 단위 테스트.

## 6. 마이그레이션 (기존 저장 데이터 호환)

- `serialize.ts`의 `SCHEMA_VERSION`을 1 → 2로 올린다. `deserializeGears`(버전 1 페이로드, `remoteLinks` 없음)를 읽을 때는 `remoteLinks: []`로 채워 넣어 하위 호환한다 — 기존에 저장된 v1 레이아웃(기어만 있고 체인/벨트 없음)은 그대로 불러와진다.
- 서버 API(`layouts` 테이블의 `gears_json`)도 동일한 버전 필드 규칙을 따름 — 스키마 마이그레이션(컬럼 추가) 불필요, JSON 페이로드 내부 버전만 올리면 됨.
